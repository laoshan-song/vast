## 一、开场：这道题到底要我们解决什么

【操作提示：打开中文首页，停在首页标题和 Q1-Q3 答案入口处。】

各位老师好。我们小组选择的是 VAST Challenge 2026 Mini-Challenge 2。这个题目可以理解为一次“系统异常溯源”任务。

题目给了我们一个异常现象：2046 年 5 月 17 日凌晨 4 点 21 分，John Windward 名下在 SaidIt 平台上出现了一条乱码帖子。公司怀疑这不是普通用户手动发帖，而是多智能体系统，也就是 Agent 系统，在自动执行任务时发生了异常。

这里的 Agent 可以简单理解为“替员工执行自动任务的软件代理”。它可能自动读文件、转发任务、检查某个平台，也可能执行发帖操作。所以我们不能一上来就说“John 本人发了帖子”。我们必须回到日志，看具体是谁执行了什么动作。

这道题要求我们回答三件事。

第一，Q1 要回答：这条异常 SaidIt 帖子是怎样一步一步产生的？也就是要还原精确事件链，并说明哪些人和系统交互参与了这件事。

第二，Q2 要回答：这些乱码帖子“意味着什么”，内容来自哪里？这里不能凭空猜正文，而是要追踪内容来源，并说明哪些结论有日志证据，哪些只是合理推断，哪些无法确定。

第三，Q3 要回答：这种行为是否已经重复发生？如果只能选一个位置做系统干预，应该选哪里，为什么这个位置最值得改。

所以我们的分析路线是：先用全局 EDA 建立正常行为基线，再找出异常发帖的字段特征，然后追踪文件和 Agent 任务链，最后比较历史事件并评估干预方案。

## 二、Overview：先建立基线，再判断什么是异常

【操作提示：进入 Overview 中文页，先展示页面顶部的“引导式分析路径”。点击第 1 步和第 2 步，让页面自动跳到对应证据面板；随后展示“统计型 EDA 图谱”，可以点击一张图放大，再关闭。】

我们先看 Overview。这里的核心作用是建立基线。因为如果不知道正常情况是什么，就无法判断目标帖子为什么异常。

原始日志一共有 185,147 条事件。Overview 的统计图先回答几个基础问题：系统里主要有哪些事件，参与对象有哪些，事件在时间上怎样分布，SaidIt 发帖在全量日志中占多大比例，以及病毒或诱饵事件是否会干扰判断。

第一张图是事件类型条形图。它说明，整个系统中大部分是常规操作，比如邮件、文件、任务和 Agent 自动化行为。SaidIt 发帖只占很小一部分。因此，我们不能只看一条帖子，而要先知道它在整个系统中处于什么位置。

第二张图是主体组成图。它告诉我们，日志里的行为主体不只有人，还有 Agent、文件系统和平台。因此，区分“人类行为”和“Agent 行为”不是主观假设，而是由数据结构本身决定的。

第三张和第四张图是时间分布图，包括小时直方图和日期-小时热力图。它们的作用是把系统运行节律展示出来，避免我们把某个时间点孤立解释。比如系统中有高密度的病毒或诱饵事件，但这些高频背景活动和三条文件源 SaidIt 帖子的机制并不是一回事。

最关键的是 SaidIt 字段审计图。全部 108 条 SaidIt 发帖里，105 条是普通人类发帖，使用的是 `content` 字段；只有 3 条是 Agent 发帖，使用的是 `content_source` 字段。`content` 表示帖子正文直接写在日志字段中；`content_source` 表示帖子正文来自一个文件。

这一步非常重要，因为它把调查入口从“乱码看起来很奇怪”变成了一个可以验证的字段特征：Agent 发帖，并且使用了 `content_source`。后面 Q1、Q2、Q3 都是围绕这三个文件源帖子展开的。

【操作提示：点击任意图下方的“查看证据视图”，或点击引导面板里的“查看当前证据”。】

网页交互也服务于这个逻辑。每张统计图下面都有“查看证据视图”。也就是说，我们不是只做静态展示，而是可以从统计图直接跳到对应的事件链、溯源图或干预矩阵。

## 三、Q1：异常帖子是怎样产生的

【操作提示：打开 Q1 中文页，先展示顶部“引导式分析路径”。点击第 2 步会跳到 EDA 图，点击第 3 步会跳到“详细视图 A：终端五步序列”。】

Q1 问的是异常帖子的产生过程。我们分四步回答。

第一步，先定位目标帖子。题目给了三个线索：SaidIt、John Windward、2046 年 5 月 17 日 04:21。我们用这三个线索在 SaidIt 发帖事件中找到目标记录。日志显示，执行发帖动作的是 John Windward 的 Agent，而且发帖字段不是普通 `content`，而是 `content_source=SwiftWren.txt`。

这说明目标帖子的正文不是 John 手动输入的一段文字，而是来自文件 `SwiftWren.txt`。因此，接下来就应该追踪这个文件和相关任务。

第二步，看发帖前后最后几秒发生了什么。Q1 的终端五步序列显示：先有一个 relay 任务到达 John Agent；接着 John Agent 执行 `saidit_post_check`；然后执行 `saidit_post(content_source=SwiftWren.txt)`；最后删除 `SwiftWren_further_instructions.md` 和 `SwiftWren.txt`。

【操作提示：点击终端序列中的一个事件框，展示 event id、time、actor、target 或 raw JSON。】

这张图说明，发帖、检查和清理文件不是分散事件，而是在几秒内连续发生的一组自动化动作。

第三步，往前追踪任务是怎么到达 John 的。我们筛选所有携带 `SwiftWren_further_instructions.md` 的 `queue_subordinate_task(task=read_file)` 事件，并按时间排序。结果显示，SwiftWren 任务链共有 186 个 relay hops，涉及 18 个 Agent，包含 119 次跨部门跳转，并且在最终发帖前 5 次到达 John。

【操作提示：在引导面板点击第 4 步，自动跳到 Agent 转发泳道图。切换 hop order 和 elapsed time；点击一个 relay 点查看细节。】

这一步说明，任务不是突然出现在 John Agent 那里的，而是在多个 Agent 和多个部门之间传播后到达 John。

第四步，追踪 `SwiftWren.txt` 的来源。文件生命周期图显示，Emma Harbor 的 Agent 先读取 `meeting_notes.doc`，随后创建 `SwiftWren.txt`。因此，在可见日志范围内，最强证据链是：`meeting_notes.doc` 被读取，生成 `SwiftWren.txt`，随后 `SwiftWren.txt` 被 John Agent 作为 `content_source` 发到 SaidIt。

所以 Q1 的答案是：异常帖子不是 John 本人手动写出的普通帖子，而是一个内部文档被打包成 payload 文件后，经过 Agent 任务链传播，最终由 John Windward 的 Agent 作为文件源发布到 SaidIt。这个过程涉及 Emma Harbor Agent、多个中继 Agent、Chloe Ballast Agent、John Windward Agent、文件系统和 SaidIt 平台。

## 四、Q2：帖子内容来自哪里，能说到什么程度

【操作提示：打开 Q2 中文页，先指向证据图例和顶部“引导式分析路径”：绿色 observed，黄色 inferred，灰色 unknown。】

Q2 问“帖子是什么意思”。这里最容易出现的问题是过度解释。因为日志没有保存完整 payload 正文，所以我们不能还原乱码原文，也不能判断人的动机。我们能做的是追踪内容来源。

Q2 页面把每起事件拆成三段：源文档、中间 payload 文件、公开 SaidIt 帖子。这样就把“乱码是什么意思”转化成了“哪个文件被作为帖子内容发布出去了”。

先看 SwiftWren。日志显示，Emma Harbor Agent 读取 `meeting_notes.doc`，随后创建 `SwiftWren.txt`，最后 John Agent 以 `content_source=SwiftWren.txt` 发帖。因此，我们可以说 SwiftWren 的可能内容主题是会议记录相关材料。但是我们不能说具体泄露了哪些句子，因为日志里没有完整正文。

再看 MellowOtter。它的链条也比较清楚：Noah Mariner Agent 读取 `strategic_directions.doc`，创建 `MellowOtter.txt`，最后由 John Agent 使用文件源方式发帖。因此，MellowOtter 的可能内容主题是战略方向材料。

HiddenOrca 要更谨慎。它的终端机制和另外两起一样，都是 Agent 使用 `content_source` 发帖并清理文件。但它的上游 source document 和 payload 创建记录在当前日志中不可见。因此，我们只能说它属于同类文件源发帖机制，不能强行指定来源文档。

【操作提示：用引导面板依次点击“先看证据完整性”“连接来源链”“明确不能声称什么”。页面会自动高亮完整性矩阵、溯源图和结论边界图。】

Q2 的几张图就是为了帮助我们守住证据边界。完整性热力图显示每起事件哪些环节可见、哪些环节缺失；证据确定性图把 observed、inferred、unknown 分开；结论边界矩阵说明哪些话可以说，哪些话不能说。

所以 Q2 的答案是：这些乱码帖最稳妥的解释是文件源发帖事件，而不是普通人类论坛文本。SwiftWren 可能来自会议记录，MellowOtter 可能来自战略方向文档，HiddenOrca 来源未知。我们能确定的是发帖机制和部分来源链；不能确定完整正文、具体机密句子、是否加密，以及人的主观动机。

## 五、Q3：这种行为是否复发，应该在哪里干预

【操作提示：打开 Q3 中文页，先展示顶部“引导式分析路径”。依次点击“证明历史复发”“比较候选干预”“给出唯一干预点”，再进入推荐网关混淆矩阵和规则权衡矩阵。】

Q3 先问这种行为会不会重复。我们的判断是：它已经重复发生。三起事件分别是 HiddenOrca、MellowOtter 和 SwiftWren。它们发生时间不同、传播规模不同、来源可见程度不同，但终端模式高度一致：任务 relay 到 John Agent，John Agent 执行 `saidit_post_check`，然后使用 `content_source` 发帖，最后删除相关文件。

Q3 的前几张图分别展示复发时间线、事件规模对比和文件源帖子的稀有性。HiddenOrca 和 MellowOtter 都发生在 SwiftWren 之前，所以 SwiftWren 不是第一次，而是同类模式的最新一次。规模图显示 SwiftWren 最大，但另外两起虽然规模小，也共享同一终端机制。

接下来要选择干预点。我们比较了几个可能方案：拦截源文件、拦截 relay 任务、只限制 John Agent、监控 delete-file，或者在 SaidIt 发布边界做拦截。

这里不能只凭直觉。拦截所有 relay 会影响大量正常自动化任务；只拦截某个文件名容易被改名绕过；只限制 John Agent 过于依赖单个端点；delete-file 报警发生在公开发布之后，已经偏晚。

【操作提示：展示 Q3 图 4 的混淆矩阵、图 5 的运维成本图、图 6 的决策权衡矩阵。】

我们推荐的唯一干预点是 SaidIt boundary gate，也就是在 SaidIt 发布边界设置规则：如果发帖主体是 Agent，并且 `saidit_post.details.content_source` 存在，就阻止发布或转人工审批。

这个方案的证据很直接。在当前数据中，它覆盖 3/3 个已观测异常文件源帖子；同时，对 105 条普通人类 `content` 帖子的观测误伤为 0。它也发生在公开发布之前，可以在内容真正外泄前拦截。

当然，这个方案也有局限。如果未来异常机制不再使用 `content_source`，而是让 Agent 直接生成普通 `content` 文本，那么还需要额外的行为检测或内容检测。但在本题“最多只能选一个干预点”的限制下，SaidIt 发布边界是证据最充分、误伤最低、工程上最可执行的位置。

## 六、可视化方法和交互亮点

【操作提示：可以回到 Overview 的“使用的可视化方法”，或快速切换 Q1-Q3 展示不同图型。】

我们这套网页不是把答案做成静态 PPT，而是让不同类型的图承担不同的推理任务。

第一类是描述性统计图，例如条形图、组成图、直方图、日期-小时热力图、堆叠条形图、矩阵和小多图。它们主要用于建立基线、发现异常字段和比较事件规模。

第二类是过程图，例如终端五步时间线、文件生命周期图和 Agent relay 泳道图。它们用于回答“事情是怎样一步一步发生的”。

第三类是证据关系图，例如 provenance graph、claim support DAG 和 confidence matrix。它们用于回答“哪些结论有证据，哪些只能推断，哪些未知”。

第四类是决策图，例如复发时间线、规模点图、UpSet 图、平行坐标、混淆矩阵和规则权衡矩阵。它们用于回答“是否复发，以及哪个干预点最合适”。

交互设计上，我们采用 overview first、filter、zoom 和 details on demand。老师可以先看六张 EDA 图理解路径，再点击“查看证据视图”跳到对应面板。进入面板后，还可以点击事件点、relay 点或候选规则，查看 event id、时间、actor、target 和原始证据。这样既能让非专业观众听懂故事，也能让专业评审检查每个结论是否有日志支撑。

总结来说，我们的核心结论是：2046 年 5 月 17 日的 SaidIt 乱码帖，不是 John 手动写出的普通帖子，而是内部文件被打包成 payload 后，经由 Agent 任务链传播，最终由 John Windward 的 Agent 作为 `content_source` 发布到 SaidIt。

我们的可视分析系统完成了三项任务：Q1 还原目标事件的精确链条和系统背景；Q2 说明帖子内容来源与证据边界；Q3 证明同类行为已经复发，并给出 SaidIt 发布边界这一单点干预方案。我的汇报到这里，谢谢老师。

## 可能追问与回答

1. 为什么不能说 John 本人发了帖子？  
因为日志显示执行 `saidit_post` 的是 John Windward 的 Agent，而且使用的是 `content_source` 文件源字段。我们可以说 John Agent 是终端发布节点，但不能把它等同于 John 本人的主观行为。

2. 为什么 `content_source` 是关键线索？  
因为正常 SaidIt 帖子主要使用 `content` 字段，而目标异常帖使用 `content_source=SwiftWren.txt`。这说明正文来自文件，所以后续分析应该追踪文件和任务链。

3. 为什么 HiddenOrca 标为 unknown？  
因为它的终端发帖机制可见，但上游 source document 和 payload create 记录不可见。为了避免 AI 幻觉或过度推断，我们保留 unknown。

4. 为什么不拦截所有 Agent relay？  
因为 relay 是系统中的常规自动化行为，全部拦截会影响大量正常任务。SaidIt boundary gate 只拦截 Agent 的文件源外部发布，在当前数据中覆盖全部已观测异常，并且对普通人类发帖的观测误伤为 0。
